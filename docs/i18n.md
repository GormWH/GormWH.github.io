# Internationalization (i18n)

The site supports three languages via URL-path locale prefixes. Translations are hand-made; missing translations render the English source content canonicalized to its original URL.

## Locale table

| Locale | URL Path | BCP-47 | html lang | og:locale | Label |
| --- | --- | --- | --- | --- | --- |
| English | `/en-us/` | en | en | en_US | English |
| Japanese | `/ja-jp/` | ja | ja | ja_JP | 日本語 |
| Korean | `/ko-kr/` | ko | ko | ko_KR | 한국어 |

**Note:** URL paths use long BCP-47 forms (language-region, lowercased); emitted language attributes use the abstract codes shown above (language-only for hreflang, language-region for og:locale).

## Fallback & canonical policy

### Real translations
When a translation exists for a given slug and locale, the page renders that content, points its canonical to itself, and joins the hreflang cluster for that slug.

### Missing translations (fallback)
When a translation does **not** exist (e.g., `/ja-jp/writing/some-slug/` but no `ja-jp/some-slug.md`), the site:
1. **Renders the English source** at the localized URL, with a visible fallback notice in the target language
2. **Points canonical** to the actual source (`/en-us/writing/some-slug/`)
3. **Excludes from hreflang** — no self-hreflang link, not part of the cluster for that slug
4. **Excludes from sitemap** — only real translations and English originals are indexed
5. **Language switcher** still points at the same logical URL (real or fallback), so links never break

### Hreflang policy
- **Language-only codes only** (`en`, `ja`, `ko` — one link per language, broadest match)
- **Plus x-default** → `/en-us/…` (English as the default for unknown locales)
- **Real translations only** — fallback pages do NOT link themselves in hreflang clusters (canonical-to-source is the SEO signal)
- **No sitemap `i18n` option** — hreflang links are hand-rolled via `alternates` prop to `BaseLayout.astro`, not auto-generated by Astro

## How to add a translation

**No config changes needed.** To add a translation for an existing article:

1. Write the file in the target locale subdir with **the same slug:**
   ```
   src/content/writing/ja-jp/closer-to-the-decisions.md
   ```
   where the English original is `src/content/writing/en-us/closer-to-the-decisions.md`.

2. Use the same frontmatter schema (title, date, tags, etc.) as the English version.

3. Rebuild: `pnpm build`

The dynamic routes automatically detect the new file and:
- Render it at `/ja-jp/writing/closer-to-the-decisions/`
- Set canonical to itself (no longer a fallback)
- Join it to the hreflang cluster
- Include it in the sitemap
- Remove the fallback notice

No `translationKey` field exists. Slugs are matched by name only.

## Language switcher

A language switcher component (in `Header` and `Footer`) appears on every page and lets users jump between locales for the same logical article.

**Behavior:**
- On a **real translation**, the switcher points to that translation's URL in the target locale
- On a **fallback page**, the switcher points to the same logical URL in the target locale (real or fallback)
  - E.g., from `/ja-jp/writing/untranslated-slug/` (fallback), switching to English goes to `/en-us/writing/untranslated-slug/`
- The switcher **never 404s** — landing pages always render

This uniform behavior preserves user intent: clicking the language flag is always safe, whether the page is fully translated or a fallback.

## Locale resolution

The router resolves locale from the `[lang]` URL segment using the central table in `src/lib/i18n.ts`. Unknown locale paths (e.g., `/xx-xx/`) are not routed; they fall through to the top-level 404.
